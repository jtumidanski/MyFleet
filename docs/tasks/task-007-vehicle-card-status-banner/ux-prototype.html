Variant 3, with the two open questions resolved: how loud the banner should be when nothing is wrong, and what it can actually say without new backend work.

Question 1 · Option A

Always-on banner

Every card gets a tinted band. Perfectly consistent — the band is always in the same place, so your eye learns one position. The cost shows up below, in the all-healthy grid.
Question 1 · Option B

Conditional banner

Tinted band only for Upcoming and Overdue. Healthy and Inactive get the same row in muted foreground on the card background — same height, same position, no color. The layout never shifts; only the urgency does.
Realism check

A garage where nothing is wrong

Your sample grid above has a convenient spread of statuses. A real personal garage is mostly Healthy most of the time — this is what each option looks like on a normal Tuesday. This is the comparison that should decide it.
Always-on
Conditional
The trade: always-on gives you a constant green reassurance signal and total consistency. Conditional means color in the grid always means "look here" — so the one Overdue truck in a garage of six is impossible to miss. Conditional is the stronger information design; always-on is the friendlier one.
Question 2

What the banner can say

I was too pessimistic earlier — most of the reason text is cheap. ScheduleStatesByVehicle already loads full QueueRows and computes DueState per row (processor.go:167-178), then narrows to []string on the way out. The due data is in memory and discarded. There's already a DueEntry shape carrying Schedule + State (processor.go:147) to widen toward.

Tier 1 — ships with the data already loaded
Tier 2 — adds the category name
Tier 1 uses NextDueMileage() vs the vehicle's current mileage (model.go:33) and the last-activity timestamp that status derivation already fetches (vehicle/status.go:45). Widening the gatherer's return type — same query, same call site.

Tier 2 needs the schedule's categoryID resolved to a display name. That's a lookup into the separate maintenancecategory domain, per vehicle, on a list endpoint — an N+1 unless it's batched, and exactly the kind of cross-domain reach CLAUDE.md warns about. Worth doing, but as its own task with a deliberate batching design.

The gap is smaller than it looks: "Service overdue by 1,120 mi" already tells you it's urgent and by how much. The category name tells you which wrench to pick up — useful, not load-bearing for a list card.
