Three directions for the admin UI

Mockups rendered in MyFleet's own tokens — the shadcn slate scale plus the semantic success / warning / danger / info families from task-003. Both themes included, so you can see how the destructive surfaces hold up on each ground.

The console has to do two quite different jobs. Most of the time it is a read tool — counts, a fleet list, drill-down. Occasionally it is a demolition tool. The three directions below differ mainly in how far they separate those two modes, and in whether the console is organised around fleets (browse, then act) or around operations (act, then watch).

Everything shown assumes the soft-delete model from the PRD: a purge stamps deleted_at, data stays recoverable for five days, and a background sweep makes it permanent. That single decision is what lets the UI show a countdown and a cancel button instead of a point of no return.

One gap worth naming up front. The UI kit at apps/web/src/components/ui/ has nine components — button, card, form, input, label, select, skeleton, switch, textarea. There is no dialog, no table, and no badge. Every direction below needs all three, so that cost is common to all of them and shouldn't sway the choice.
Direction A

In-shell section

Admin is one more entry in the existing sidebar. Same AppLayout, same chrome, same table patterns as the rest of the app. The cheapest thing that works — and the one that most easily lets a destructive action feel routine.

The only signals that this screen is different from the rest of the app are the red nav label and the red outline buttons. A fleet pending purge stays in the list, struck through, with a countdown — that's the soft-delete window made visible, and it's the pattern all three directions share.

Buys you
Lowest build cost. Reuses AppLayout, existing nav, existing page conventions. One new route group, five pages, no new layout component.
Costs you
No mode boundary. "Purge" sits in the same visual register as "Add vehicle", and the sidebar offers a one-click path from ordinary use to a system wipe.
Fits if
You're the only admin, you trust yourself, and you'd rather ship the capability than the ceremony around it.
Direction B

Dedicated console, operations-first

/admin swaps to its own layout with a persistent mode band across the top. The landing screen is the purge queue, not the fleet list — because the thing that actually needs watching is work already in flight, inside its recovery window.

The mode band is the whole point of this direction — it's present on every admin screen and states the blast radius in plain words. Status copy avoids system vocabulary: "Recoverable" and "Media not deleted" rather than pending and partial, which is what the API actually calls them.

Buys you
Unmistakable mode. Partial failures get a first-class home instead of hiding in a toast, and the recovery window is the organising idea rather than a footnote.
Costs you
A second layout component and its own nav. Fleet browsing — the thing you asked for first — becomes a secondary screen.
Fits if
You expect purges to be routine enough that watching them matters more than finding fleets.
Direction C

Dedicated console, fleet inspector

Same dedicated chrome as B, but the organising object is the fleet. A persistent list on the left, detail on the right, and the delete control sits directly beneath a live count of exactly what it would destroy. You cannot reach the button without passing the blast radius.

The blast-radius panel is the distinguishing move: the counts are rendered from the same query the purge itself would run, so what you read is what you'd destroy. Owner's "Remove" is inert — a fleet can't lose its only owner.

Buys you
Browsing and deleting are the same motion, and the consequence is always on screen. Best answer to "see a list of fleets, and information relevant to them".
Costs you
Two-pane layout needs a real responsive story on narrow screens. The blast-radius counts need a dedicated endpoint that's exact rather than approximate.
Fits if
Inspection is the common case and deletion is the occasional consequence of it — which matches how you described wanting to use this.

For a system purge the same dialog asks for PURGE EVERYTHING and names what survives — user accounts, sign-ins, and the seeded maintenance categories — because "everything" is otherwise a frightening and inaccurate word.

Why the copy reads the way it does

  • Consequence before mechanism. "14 vehicles and 3,108 related records belonging to 6 people" — the people are the part that matters, and it's the part a row-count alone hides.
  • An explicit expiry, not a duration. "until 7 August, 2:03 pm" beats "for 5 days" because you can act on a date without doing arithmetic.
  • No apology, no hedging. The dialog states what happens and offers a way out. It doesn't ask whether you're sure — the typed phrase already answered that.

Recommendation

C, with B's purge queue kept as a peer section — which is roughly what the nav in the C mockup already shows. The reasoning:

  • You asked for fleet browsing first. "See a list of fleets, and information relevant to them" was the granular requirement; C makes that the centre and B makes it a side trip.
  • The separate shell solves a real routing problem for free. After a system purge you have no fleet, and RequireAuth currently bounces fleetless users to /onboarding. A dedicated console makes the exemption structural rather than a special case bolted onto the shared guard.
  • The blast-radius panel is cheap insurance. It needs the counts the purge endpoint computes anyway, so it's presentation of data you already have — and it turns "delete this fleet" from a leap into a read.

A is the honest fallback if the two-pane responsive work looks like too much for a first pass. It's a real option, not a straw man — you'd be trading the mode boundary for maybe a third less frontend work.

Still unresolved, and it shows up in the mockups. Direction C's blast-radius panel lists "Notifications · 6", but notifications look user-scoped rather than fleet-scoped. If a person belongs to two fleets, that number — and the delete behind it — could reach into a fleet you never targeted. That's open question 2 in the PRD and R4 in the risk register, and it needs settling at /design-task before any of these screens get built.
