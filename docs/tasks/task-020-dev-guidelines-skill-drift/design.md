## 1. What This Design Changes About the PRD

The PRD scoped this task to `.claude/skills/**`. Verification during design found that scope cannot reach the stated goal, and found three drift classes the specification inventory missed. Both are resolved below; §2 records the decisions, §3 the new evidence.

### 1.1 The checklists are not in the skills

`grep -rln "DOM-0\|SUB-0\|SEC-0\|FE-0" .claude/` returns exactly two files, and neither is a skill:

- `.claude/agents/backend-guidelines-reviewer.md` (198 lines)
- `.claude/agents/frontend-guidelines-reviewer.md` (167 lines)

The skills are the *prose* those agents read in Phase 0. The normative, ID-bearing checks — the things a reviewer actually reports PASS/FAIL against — live in the agent definitions. PRD §2 Goal 2 ("the reviewer agents can run their checklists literally, without setting any item aside, and produce zero false positives attributable to guideline drift") and PRD §10's acceptance criterion ("neither sets any checklist item aside as inapplicable") are therefore unreachable by editing skills alone. The false positives are generated by text in the agent files.

This is not a judgment call about thoroughness. Six backend checks and two frontend checks are *provably* broken against this tree — see §3.1.

**Resolution:** both reviewer agent definitions are in scope. PRD §9's open question is closed as "fold in."

### 1.2 Two additional drift classes

`file-responsibilities.md`'s `administrator.go` contract and both agents' invocation commands are drifted in ways the specification inventory did not record. See §3.2 and §3.3.

## 2. Design Decisions

### D1 — Scope includes both reviewer agent definitions

**Decided:** fold `.claude/agents/backend-guidelines-reviewer.md` and `.claude/agents/frontend-guidelines-reviewer.md` into scope.

*Alternatives considered.* (a) Backend agent only — the backend drift is more severe (6 broken checks vs 2), but the frontend agent's Phase 1 gate runs `cd frontend && npm test -- --watchAll=false`, which fails outright on a repo whose web app is at `apps/web` and whose runner is Vitest. A reviewer that cannot complete Phase 1 is worse than one emitting false positives. (b) Skills only, follow-up issue — rejected: it leaves the pre-PR gate emitting `DOM-03`/`DOM-10`/`DOM-17` failures on *every* Go domain indefinitely, which is the exact defect this task exists to remove, and it means shipping a task whose own acceptance criteria cannot pass.

*Cost.* The diff grows by ~365 lines of reviewable prose across two files. Both are self-contained and neither is loaded into ordinary agent context (only when a reviewer is dispatched), so §8's token-budget constraint is unaffected.

### D2 — Dead checks are replaced by their nearest real invariant, IDs retained

`DOM-09` ("Transform errors handled") and `DOM-17` ("JSON:API interface on REST models") describe api2go mechanics that have no analogue here: `Transform` returns `server.Resource` with no error (`apps/fleet-service/internal/vehicle/rest.go:58`), and no `GetName`/`SetID` exists anywhere in the tree. They cannot be re-grounded; they can only be replaced or deleted.

**Decided:** replace, keeping the IDs.

| ID | Was | Becomes | Grounded in |
| --- | --- | --- | --- |
| `DOM-09` | Transform errors are not discarded | Handlers route every domain error through `server.WriteError(w, err)`; no hand-built error envelope, no bare `http.Error` | `packages/shared-go/server/jsonapi.go` · `vehicle/resource.go:38` |
| `DOM-17` | RestModel implements `GetName()`/`GetID()`/`SetID()` | `rest.go` returns `server.Resource` with a literal `Type` string and the model's ID; the JSON:API `type` is not computed or reflected | `vehicle/rest.go:76` |

*Alternatives considered.* Deleting with ID gaps honors PRD §2's "no change to checklist semantics" most literally, but trades two live invariants for nothing — both replacements guard real, currently-unchecked properties at the same altitude as the checks they succeed. Deleting and renumbering was rejected outright: `docs/tasks/*/audit.md` files already cite DOM numbers, and renumbering silently changes what those historical records mean.

Each replacement is recorded in the Phase 3 rule inventory as **replaced**, with the evidence above as its reason. This is the one place where this task changes checklist semantics; it is deliberate and bounded to two rows.

### D3 — `patterns-provider.md` is rewritten in place and absorbs the write side

**Decided:** keep the filename; rewrite it as the real data-access pattern covering **both** `Provider` and `Administrator`.

Today the read side is documented twice (`patterns-provider.md` in full, `file-responsibilities.md § provider.go` again) and the write side once (`file-responsibilities.md § administrator.go`) — and all three are wrong. Splitting a read/write pair across two files is what let the write side drift unnoticed while the read side was at least *noticed*. After the rewrite, `patterns-provider.md` owns the contract; `file-responsibilities.md` keeps one-line role statements that point at it.

*Alternatives considered.* Deleting the file and folding everything into `file-responsibilities.md` means one fewer file to drift, but `file-responsibilities.md` is a per-file *role* reference — thirteen one-paragraph sections — and the data-access contract needs a worked example of the `gorm.ErrRecordNotFound` → `ErrNotFound` translation and the `server.Page` threading. Burying that in a role index makes it less likely to be read. Rewriting provider-only was rejected because it leaves the drifted `Administrator` contract in a file nobody flagged.

### D4 — Rule inventory is rule-level, produced per-file in Phase 3

PRD §8 and §10 call for a keep/fix/delete disposition for every normative rule. There are ~4,750 lines across 25 files.

**Decided:** `design.md` carries the file-level disposition table (§6) for all 25 files. `plan.md` opens each file's task with that file's rule-level keep/fix/delete/replace rows, and the rewrite commit for that file carries them.

*Rationale.* The inventory exists to stop a rule being silently dropped. It only does that if the person doing the dropping is looking at it — which is at rewrite time, not two phases earlier. Writing it here would mean transcribing 4,750 lines before a single design decision is acted on, and the transcript would be re-read in Phase 3 anyway.

*This deviates from the AC's "design-phase" wording.* The Phase 3 plan must therefore make the inventory a hard per-task deliverable, not a note — see §10.

### D5 — `skill-rules.json` gets backend file triggers

Not in the PRD. `skills.backend-dev-guidelines.fileTriggers.pathPatterns` is `[]`. The backend skill has **never** auto-suggested on a Go file change; it fires on prompt keywords only. PRD §1 and CLAUDE.md both assert otherwise, and PRD §10 asks the audit to confirm "the `skill-activation-prompt` hook still fires on a Go file change" — a check that cannot pass today and would not pass after a correct rename either.

**Decided:** populate the backend `pathPatterns` (`apps/*/internal/**/*.go`, `packages/shared-go/**/*.go`, `packages/dto-go/**/*.go`, with `**/*_test.go` excluded to match the frontend entry's convention), and drop the dead `frontend/**/*.ts` / `frontend/**/*.tsx` patterns from the frontend entry. The surviving frontend patterns (`**/components/**/*.tsx`, `**/pages/**/*.tsx`, `**/lib/hooks/**/*.ts`, `**/lib/schemas/**/*.ts`, `**/services/api/**/*.ts`) already match real `apps/web/src` paths and stay untouched.

This is not the `.claude/settings.json` hook wiring PRD §2 excludes — that file is unchanged. It is the trigger data the wiring reads, and it is part of "the skills."

The `notes.customization` block still carries the prior project's `blog-api` example values (PRD §9). It is inert configuration documentation; corrected in the same commit since the file is already open.

### 3.2 `administrator.go` contract is fully drifted

Not recorded in `drift-inventory.md`. `file-responsibilities.md` documents free functions taking `*gorm.DB` first and returning `Entity`:

```go
func create(db *gorm.DB, name string) (Entity, error)
func update(db *gorm.DB, id uuid.UUID, name string) (Entity, error)
func deleteByID(db *gorm.DB, id uuid.UUID) error
```

The real pattern is an exported interface plus a `db`-backed implementation, taking and returning `Model`, with `uuid.UUID` nowhere in sight (`apps/fleet-service/internal/vehicle/administrator.go:15-32`):

```go
type Administrator interface {
    Insert(Model) (Model, error)
    InsertWithHooks(m Model, hooks ...TxHook) (Model, error)
    Update(Model) (Model, error)
    SoftDelete(id string) (Model, error)
    ...
}

func NewAdministrator(db *gorm.DB) Administrator { return &dbAdministrator{db: db} }
```

The documented rationale ("the processor converts via `Make`") is also wrong: the administrator calls `Make` itself and hands back a `Model`.

Also drifted in the same file and not previously recorded: `Make(Entity) (Model, error)` (real: no error), and the `provider.go` "Typical Signatures" block using `uint32` IDs.

**Worth adding** (present in code, absent from the guidelines): `TxHook` — side-effecting work that must commit or roll back with the write runs on the insert's transaction, and hook errors are fatal to the whole transaction (`vehicle/administrator.go:9-12,43`). This is the write-side analogue of the `ErrNotFound` translation on the read side.

### 3.3 Frontend `architecture-overview.md` is structurally, not just lexically, drifted

`drift-inventory.md` §E marked this file verified. It is not. Its "Project Structure" tree and "Key Configuration" section assert:

| Claim | Reality |
| --- | --- |
| Root is `frontend/` | `apps/web/` |
| `components/common/` | Does not exist (`admin/`, `features/`, `frame/`, `providers/`, `ui/`) |
| `lib/breadcrumbs/` | Does not exist |
| `types/api/` | Does not exist; API types come from `@myfleet/shared-ts` |

## 4. Architecture

### 4.1 Two tiers, one source of truth

```
                     ground truth
              apps/**/internal/**  ·  packages/shared-go/**  ·  apps/web/src/**
                              │
                              │  every normative claim traces to a file:line here
                              ▼
        ┌─────────────────────────────────────────────────┐
Tier 1  │  .claude/skills/{backend,frontend}-dev-guidelines │  prose + worked examples
        │  SKILL.md + resources/*.md            (23 files) │  read by implementing agents
        └─────────────────────────────────────────────────┘
                              │  Phase 0 read list
                              ▼
        ┌─────────────────────────────────────────────────┐
Tier 2  │  .claude/agents/{backend,frontend}-guidelines-    │  ID'd binary checks
        │  reviewer.md                           (2 files) │  read by reviewer agents
        └─────────────────────────────────────────────────┘
                              │
                              ▼
                  docs/tasks/<task>/audit.md
```

The invariant this design establishes, and which the rewrite must not break: **a Tier-2 check may only assert something a Tier-1 file states, and a Tier-1 statement may only assert something a ground-truth `file:line` shows.** Today the chain is broken at both joints — Tier 2 asserts `Make` returns an error that Tier 1 also (wrongly) claims, and neither matches the code.

### 4.2 Rewrite strategy by drift class

Files are not all broken the same way, and treating them uniformly is how the current state arose. Five classes, each with a different procedure and a different risk of silent rule loss:

| Class | Procedure | Silent-drop risk |
| --- | --- | --- |
| **R — Rebuild** | Delete the body, write fresh from the canonical source files in §5. Preserve only rules the inventory marks *keep*. | **High** — every rule must be inventoried before deletion |
| **S — Surgical** | Section-scoped replacement of a drifted contract; surrounding prose untouched | Medium — bounded to named sections |
| **V — Vocabulary** | Mechanical domain substitution + path/identifier correction. Structure and rules unchanged. | **None** — no rule can be lost by renaming its example |
| **C — Check re-ground** | Per-row edit of a checklist table; the row's *intent* is preserved, its *verification recipe* is rewritten | Medium — replaced rows need explicit reasons |
| **M — Metadata** | Frontmatter / JSON config | None |

Class V is the bulk of the line count and carries no correctness risk, which is why §2 D4's per-file inventory is affordable: the inventory work concentrates in the R and S files.

### 4.3 Domain substitution map

One map, applied consistently, so the same concept doesn't become three different vehicles across files:

| Prior-project concept | MyFleet analogue | Real source |
| --- | --- | --- |
| bucket (primary aggregate) | vehicle | `apps/fleet-service/internal/vehicle` |
| policy (child config of the aggregate) | maintenance schedule | `apps/fleet-service/internal/maintenanceschedule` |
| ban (list-with-filters resource) | invite | `apps/fleet-service/internal/invite` · `apps/web/src/lib/hooks/api/invites.ts` |
| replication (long-running triggered op) | purge | `apps/fleet-service/internal/vehicle/purge.go` · `internal/admin` |
| `bucketarchive` (sub-domain action-event) | `vehiclemedia` | `apps/fleet-service/internal/vehiclemedia` |
| `policyrevoke` | `mileage` | `apps/fleet-service/internal/mileage` |
| read-only aggregation handler | dashboard | `apps/fleet-service/internal/dashboard` |
| cross-domain orchestration ("create bucket also creates default policy") | creating a vehicle also records activity and emits an event | `vehicle/resource.go:29-31` (`WithActivityRecorder`, `WithEventEmitter`) |

## 7. The `@/` Alias Question

`FE-03` and 8 frontend resource files write imports as `@/lib/...`. No alias exists. There are two ways to make the guidelines true, and they are not equivalent:

**Chosen: correct the docs to relative imports.** PRD §2's first non-goal is "no application code changes; this task touches `.claude/**` only." Adding the alias means editing `tsconfig.app.json` and `vite.config.ts`, which is application configuration, and — to be meaningful — rewriting hundreds of existing imports. That is a separate task with its own review surface.

**Rejected: add the alias.** It is the nicer end state, and `apps/web/src/lib/hooks/api/vehicles.ts` importing `'../../../services/api/VehicleService'` is evidence the relative paths are getting deep. But adopting it here would mean the guidelines document a convention almost no existing file follows — trading one flavor of drift for another, and violating FR-7.4 ("if a documented practice is aspirational rather than current, either implement it or drop it").

Filed as a follow-up (§11). Until then the guidelines describe relative imports, because that is what the code does.

## 8. Sequencing

PRD §8 asks for per-file commits. Ordering matters beyond reviewability: the Tier-1 rebuilds establish the vocabulary the Tier-2 checks then cite, so doing Tier 2 first would mean writing checks against prose that does not exist yet.

1. **Ground truth** — no commit. Confirm the §5 canonical set compiles and reflects current `main`.
2. **Backend R files** — `patterns-provider.md`, then `patterns-rest-jsonapi.md`. Two commits. These define the API vocabulary everything downstream reuses; doing them first means later files quote rather than re-derive.
3. **Backend S files** — `file-responsibilities.md`, `patterns-functional.md`, `architecture-overview.md`, `anti-patterns.md`, `ai-guidance.md`, `testing-guide.md`, `scaffolding-checklist.md`. One commit each.
4. **Backend M** — `SKILL.md` frontmatter rename. Separate commit, so if FR-5.2's verification fails the revert is surgical.
5. **Frontend R/S files** — `architecture-overview.md` first (it defines the tree and config every other file references), then service-layer, types, api-client, react-query, testing-guide, forms, components, routing, anti-patterns, ai-guidance, styling, `SKILL.md`.
6. **`skill-rules.json`** — one commit.
7. **Tier 2** — `backend-guidelines-reviewer.md`, then `frontend-guidelines-reviewer.md`. Last, so every check can cite a Tier-1 file that already says the right thing.
8. **Verification** — §9. Fixes land as follow-up commits, not amendments, so the audit trail survives.

Steps 2–5 are internally independent per file: nothing in step 3 blocks anything else in step 3.

## 9. Verification

Four gates, in order. Gate 4 is the only one that actually tests the PRD's goal; gates 1–3 exist to make gate 4 cheap.

**Gate 1 — mechanical greps.** All ten from PRD §10, run as one script committed to the task folder so the audit can re-run it verbatim. Two need care: the `services/` guard must not flag the legitimate frontend `services/api/`, and the Jest guard must not flag `@testing-library/jest-dom`. Extended with three checks this design adds:

```sh
grep -rn "RestModel\|GetName()" .claude/                    # 0
grep -rn "from '@/" .claude/skills/frontend-dev-guidelines/ # 0
grep -rn "__mocks__\|watchAll\|Methods(http.Method" .claude/ # 0
```

**Gate 2 — identifier existence.** For every Go identifier appearing in a rewritten `.claude/skills/backend-dev-guidelines/` code block, grep `packages/shared-go` and `apps/*/internal/*` for a definition. Zero misses. This is PRD FR-7.2 made executable without a build harness; the §5 canonical set is what makes it tractable.

**Gate 3 — non-regression.**
- `git diff --name-only main...HEAD` touches nothing under `apps/`, `packages/`, `deploy/`.
- `make ci` passes (expected trivially — it confirms nothing was touched by accident).
- Every path named in a guideline resolves: `Skill("backend-dev-guidelines")` loads post-rename; `skill-activation-prompt` fires on a Go file change (which requires D5 — it does not fire today).

**Gate 4 — the real test.** Dispatch both reviewers against a recent merged task's diff. Success is not "the audit passes" — it is:

- Neither reviewer sets any checklist item aside as inapplicable.
- No finding is traceable to guideline drift.
- Every `DOM-*` / `FE-*` row produces a `file:line` citation for PASS or FAIL — no row silently vacuous.

That last clause is the one `DOM-08` and `FE-03` would fail today by *passing*: a grep that can never match reports PASS with no evidence. The audit must show a citation per row, not a status per row.

Target diffs: task-017 (`app-frame-navigation`) for frontend, per PRD §10. For backend, a diff that touches a full domain package is needed to exercise `DOM-01`–`DOM-19`; task-014 (`member-names-ownership-transfer`) or task-013 (`media-card-image-variant`) are the candidates — Phase 3 picks one and records why.

## 10. What Phase 3 Must Produce

Beyond ordinary task decomposition, `plan.md` must carry three things this design deliberately did not:

1. **Per-file rule-level inventory (D4).** Every task for an **R** or **S** file opens with a keep / fix / delete / replace table over that file's normative rules, and every *delete* and *replace* carries a stated reason. **V**, **C**, and **M** files may use section-level rows. This is the PRD's no-silent-drop guarantee; without it, D4's deviation from the AC is unbacked.
2. **A disposition for `scaffolding-checklist.md` §4/§5/§6** (§3.4). Deleting three sections of a checklist is a bigger call than the rest of this task; the plan should verify against `deploy/k8s` and `.github/workflows` and state the outcome rather than leaving it to the implementer.
3. **A disposition for `testing-guide.md`'s mock convention** (~90 lines). Check the real convention across the 108 `*_test.go` files first; the section is kept, rewritten, or dropped on that evidence, not on preference.
